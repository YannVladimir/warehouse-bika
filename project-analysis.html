Archive Document Location Management System

Complete analysis of the existing frontend + backend prompt, with a clear implementation roadmap. Read this before writing a single line of backend code.

1 What This System Is

Core concept: A physical document location tracking system — like a library catalogue but for warehouses. Users don't store or retrieve files. They look up a document number and the system tells them exactly where to walk inside the warehouse to find the physical paper document.
📦
No file storage
The system tracks WHERE documents are, not the document content. No PDF uploads, no S3 buckets.
🏭
Physical location hierarchy
Warehouse → Zone/Building → Shelf → Box → Document. The path tells a person where to physically go.
🏢
Multi-tenant (per company)
Multiple companies share one system. Company A cannot see Company B's documents or warehouses. Hard data isolation.
🔐
Three-tier access control
Super Admin (global), Company Admin (per company), User (read + search only). Each role has strict capabilities.
🔍
Primary use case: Search
A standard user types a document number or title and instantly gets its shelf address. That's the core workflow.
📊
Secondary use case: Management
Admins register new documents, set up warehouses, manage shelves, assign documents to locations.
📋
Audit & history
Every search is logged. Every document move is recorded. Admins can see who looked for what and when.
⚡
Performance matters
Millions of documents possible. Document number search must be indexed and fast. Company-level filtering on every query.
In one sentence: Bika Archive is a multi-tenant, role-based warehouse catalogue — users search for a document number, the system responds with a physical address inside a warehouse.

3 Critical Decision — Location Hierarchy

Conflict detected: The backend prompt defines a deeper hierarchy than what the frontend has already built. You need to decide which to use before writing backend code.
Frontend (Already Built)
  • Company
  • Warehouse
  • Zone (= simplified "Area")
  • Shelf
  • Box
  • Document

4 levels deep. Simple, already implemented in the UI.

Backend Prompt (Full Hierarchy)
  • Company
  • Warehouse
  • Building
  • Floor
  • Room
  • Rack
  • Shelf
  • Box
  • Document

8 levels deep. More granular for large physical warehouses.

Recommendation: Meet in the middle with a configurable hierarchy
Design the backend with a generic LocationNode table (id, parent_id, type, name, company_id) using a self-referencing tree. This means the hierarchy is fully flexible — the frontend's Zone maps to a node of type ZONE, but you can add Building/Floor/Room in future without schema changes. The frontend only sees the levels it knows about (Warehouse → Zone → Shelf → Box). This is the cleanest approach and avoids rebuilding the frontend.

6 Backend Tech Stack Decision

Java 21 Spring Boot 3.3 Spring Security 6 Spring Data JPA PostgreSQL 16 Flyway JWT (jjwt 0.12) Swagger / OpenAPI 3 MapStruct Lombok Docker + Docker Compose Maven

MapStruct handles DTO↔Entity mapping at compile time (zero reflection overhead). Flyway handles all schema migrations — never run raw SQL manually. Docker Compose will run both PostgreSQL and the Spring app locally.

8 Decisions to Make Before Sprint 1

1. Location hierarchy depth
Stick with frontend's Warehouse → Zone → Shelf → Box and map it to a flexible LocationNode tree? Or rebuild the frontend to match the full Building → Floor → Room → Rack hierarchy? Recommended: keep frontend as-is, use flexible tree backend.
2. Multi-tenancy strategy
Schema-per-tenant (separate PostgreSQL schemas per company) vs. row-level security (shared tables, company_id filter)? Recommended: row-level with company_id on every tenant-scoped table — simpler to deploy, easier to migrate.
3. Search strategy
Simple ILIKE queries vs. PostgreSQL full-text search (to_tsvector) vs. Elasticsearch? Recommended: start with PostgreSQL full-text search (built-in, no extra infrastructure). Add Elasticsearch only if performance demands it later.
4. Token storage on frontend
Store JWT access token in memory (most secure) + refresh token in httpOnly cookie? Or both in localStorage (simpler but XSS risk)? Recommended: access token in memory + refresh token in httpOnly cookie.
5. Email service for password reset
Need SMTP for Sprint 8 password reset flow. Plan to use SendGrid, Mailgun, or local MailHog for dev? Decide early so config is ready.

9 Where to Start

Sprint 1 first commit should produce: A running Spring Boot app → Docker Compose spins up PostgreSQL → Flyway creates the companies + users tables → POST /api/auth/login returns a real JWT → Swagger UI is live at /swagger-ui.html. Everything after Sprint 1 builds on this foundation.
Frontend integration tip: In parallel with Sprint 1, create an api.js service in the frontend with Axios, add a JWT interceptor, and replace the mock auth context with real login — this unblocks testing the two sides together from day one.
